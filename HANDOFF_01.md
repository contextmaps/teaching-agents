# HANDOFF_01 — Platform Skeleton

**Project:** Pamplin AI Agent Recipes (`teaching-agents`)
**Spec reference:** `SPEC.md` v0.1
**Cut:** Foundational — builds the full site skeleton with placeholder recipe content, ready for real recipe authoring in HANDOFF_02 and beyond.

---

## Goal of this iteration

Stand up the full static-site skeleton: build pipeline, design system, all 23 recipe pages with placeholder content, all 4 platform tutorial pages with placeholder content, NotebookLM appendix page, About page, and the catalog home page. The site should look complete and navigate cleanly end-to-end, even though the load-bearing recipe Instructions text is intentionally placeholder.

After this handoff, the project has a working `dist/` that can be opened in a browser, where every page renders, every link works, every copy button fires, and the analytics pipeline is wired (pending Form ID population).

What this handoff explicitly **does not** include:
- Real recipe Instructions text. Each recipe ships with placeholder text clearly marked as such.
- Real screenshots. Tutorials use placeholder image slots.
- Real About page copy beyond a short paragraph stub.
- Production Google Form IDs. Config carries placeholder values until Onur creates the form (see Form Setup Guide, deliverable D5).

### Part 2 — Design system and templates

**D2.1 Single stylesheet at `assets/css/styles.css`.**

Adapt the workshop platform's `:root` tokens, applying the maroon overrides from SPEC §5. All `plib-*` utility classes the recipes site uses are reproduced here:
- `plib-skip-link`, `plib-wrap`, `plib-page-header`
- `plib-copy-btn` with success state
- `plib-textarea` (used for the long Instructions field display)
- Focus-visible outlines, screen-reader hidden classes

Plus new styles for the recipes site:
- Catalog grid (responsive: 3-col → 2-col → 1-col)
- Family section headers (maroon underline accent, generous top margin to separate sections)
- Recipe card (uniform size, hover state, tier badge, platform badge)
- Recipe page layout (breadcrumb, title block, framing paragraph, field stack)
- Tier badge styles (light / medium / heavy variants per SPEC §5 tokens)
- Tutorial page layout (text-led with optional image slot — see Part 3 for tutorial structure)

**Single CSS file, no preprocessor.** Inherits the workshop platform's discipline of single-file simplicity.

**D2.2 Single JS file at `assets/js/site.js`.**

Two responsibilities:
1. **Clipboard handling.** When a copy button is clicked: read its target field text, write to clipboard via `navigator.clipboard.writeText()`, update button to success state, fire analytics event, revert after 2 seconds. Fall back to a textarea-select trick if clipboard API unavailable (parity with workshop platform).
2. **Analytics.** Fire `page_view` on page load. Fire `field_copied` on copy click. Fire `tutorial_step_viewed` if anchored navigation is implemented (skip for v1 if simpler). Use the `submitToGoogleForm()` helper pattern from the workshop platform's `index.html`. Session ID generated per browser session via `sessionStorage`, UUID v4.

**D2.3 Templates in `templates/`:**

- `base.html` — root template: HTML scaffold, header strip with site title and tagline, top nav (Home · Tutorials · About), footer ("Made for Pamplin College of Business · Last updated [date]"), styles + script tags.
- `catalog.html` — extends base. Renders the home page: brief intro paragraph, then 7 family sections each with their recipe cards (always-expanded per design decision). Tutorial section below the catalog with its own separator.
- `recipe.html` — extends base. Renders a single recipe page per the layout in SPEC §7.
- `tutorial.html` — extends base. Renders a single platform tutorial: title, intro paragraph, numbered text-based steps, optional single screenshot at top of page (per the screenshot decision in this handoff — see Part 3).
- `notebooklm.html` — extends base. Renders the NotebookLM appendix page.
- `about.html` — extends base. Renders the About page (placeholder copy in this handoff; final copy in a later handoff).

Templates use semantic HTML, respect the workshop platform's accessibility primitives (skip link, aria-live announcement region for copy-button success, focus-visible outlines, aria-labels on all icon-only buttons).

### Part 3 — Tutorial format decision (text-led, one screenshot per platform)

**Adopting the hybrid format per Onur's feedback.** Each tutorial:

- Opens with a single anchoring screenshot showing the entry point ("this is what you click to start"). One screenshot per platform = 4 total + 1 for NotebookLM = 5 screenshots site-wide.
- Body is **text-based numbered steps** (3 steps minimum: Entry → Creation form → Save & share). Each step is 2–4 sentences in prose.
- Field-mapping table: a small two-column table mapping the platform's field labels to the recipes' terminology (e.g., for ChatGPT: "Name → Title, Description → Description, Instructions → Instructions, Knowledge → Knowledge Base, Capabilities → Tools").
- "Last updated" date in the page footer — populated when the tutorial is verified current.
- For Copilot tutorial only: the one-paragraph note about Copilot Studio at the bottom (per SPEC §8).

### Part 6 — Documentation artifacts

**D6.1 `JIM_INTEGRATION_NOTES.md` at repo root.** ≤ 1 page. Sections:

1. **Site URL.** `https://contextmaps.github.io/teaching-agents/`. Hosted by Onur via GitHub Pages. No deployment needed by Pamplin IT.
2. **Optional iframe wrapping.** If Pamplin IT wants to embed the recipes site inside a Pamplin-branded page, here's the suggested markup:
   ```html
   <iframe src="https://contextmaps.github.io/teaching-agents/"
           style="width:100%; height:1800px; border:0;"
           title="Pamplin AI Agent Recipes"
           loading="lazy"
           allow="clipboard-write"></iframe>
   ```
   Note: `allow="clipboard-write"` is required for the per-field copy buttons to work inside an iframe. Without it, clipboard copy fails silently. The site itself doesn't need any header-suppression flag — the maroon header is part of the site identity and renders fine inside or outside a wrapper.
3. **Data capture.** Behavioral analytics (page views, copy clicks) go to a Google Form owned by `contextmaps@gmail.com`. No backend infrastructure to maintain.
4. **What can fail.** GitHub Pages outage (unlikely; cached). Google Form outage (extremely unlikely; analytics silently fail and the site continues working). Recipe content is static so faculty browsing is never blocked by infrastructure.
5. **Updates over time.** Recipe content is calibrated and refined post-launch. Updates ship as commits to the `contextmaps/teaching-agents` repo; GitHub Pages picks them up automatically. No coordination needed.
6. **Contact.** Onur Seref for design questions. Jim Dickhans for institutional / IT questions, including Copilot Studio access for faculty who want to deploy at the institutional tier.

**D6.2 `FORM_SETUP_GUIDE.md` at repo root.** A short guide (≤ 1 page) for Onur to follow when he creates the Google Form. Sections:

1. **Form structure.** Four short-answer questions: `type`, `session_id`, `timestamp`, `payload`. Order matters for the `entry_*` ID extraction.
2. **Why no `name` / `email` fields.** Anonymous behavioral capture only.
3. **How to extract the four entry IDs.** Step-by-step: open the form's "Get pre-filled link" feature, fill each field with a placeholder string ("TYPE", "SESSION", "TIMESTAMP", "PAYLOAD"), generate the prefilled URL, copy the URL, identify each `entry.NNNNNNNN` parameter and which field it corresponds to (the prefill values you typed appear next to the entry IDs in the URL).
4. **Where to put the values.** Edit `config.json`'s `form` block, replace the four placeholder entry IDs and the `submission_url`.
5. **How to verify.** A small `curl` command Onur runs from the terminal to confirm the form accepts a test submission. Format:
   ```bash
   curl -X POST 'https://docs.google.com/forms/d/e/YOUR_FORM_ID/formResponse' \
     -d 'entry.XXXX=test&entry.YYYY=test-session&entry.ZZZZ=2026-05-09T12:00:00Z&entry.WWWW=test-payload'
   ```
   Then check the Google Sheet for the row.
6. **What to do if a test submission doesn't appear.** Common causes: wrong submission URL (it must be the `formResponse` endpoint, not the form's view URL), wrong entry IDs, form set to require sign-in. Each has a one-line fix.

This guide is the artifact Onur uses when he sets up the form post-handoff.

## Constraints

- **No new dependencies beyond Jinja2.** No CSS preprocessor, no JS framework, no build tooling beyond `python3 build.py`.
- **No hash-routing or client-side router.** Every page is a real `.html` file in `dist/`.
- **No localStorage** (the workshop platform's pattern). `sessionStorage` is fine for session ID.
- **No JavaScript-required navigation.** All links are real `<a href>` and work without JS. JS is enhancement (clipboard, analytics) not requirement.
- **Light theme only.** No dark mode toggle.
- **No external font CDN.** System font stack inherited from workshop platform (`-apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif`).
- **Recipe content is placeholder only.** CC must not author real Instructions text. The point of this handoff is the skeleton; real authoring is a later handoff with explicit calibration.
- **Visible DRAFT banner on every recipe page** until real Instructions land. Removable via a single CSS class flip.
- **Single-file CSS, single-file JS.** Embedded `<style>` and `<script>` tags acceptable in `base.html` if preferred, or external `assets/css/styles.css` and `assets/js/site.js` — CC's choice. Prior project precedent is embedded; recipes site has 23+ pages and may benefit from external. CC picks based on file size and maintainability.

## Notes for CC

- **Inherit from the workshop platform aggressively.** When in doubt about CSS conventions, copy buttons, focus rings, or accessibility primitives, look at the workshop platform's `index.html` and replicate. The recipes site is the workshop platform's design DNA with maroon overrides and a multi-page architecture.
- **The maroon override is the visible difference.** Blue (`#1a5da0`) was the workshop's dominant accent; here, maroon (`#861F41`) takes that role. Blue stays in use only for hyperlinks and focus rings (accessibility-driven).
- **23 recipe JSON files is a lot to write by hand.** CC may want to write a small generator script that takes the catalog table from SPEC §6 and produces the 23 JSON skeletons in one pass, then fill in details. This is a CC implementation choice; either approach is fine as long as the resulting files are clean and match the schema.
- **Placeholder Instructions text is intentional.** Do not author real Instructions content. The whole point of this handoff is to prove the architecture; real content is the work of HANDOFF_02 onward, with explicit calibration cycles.
- **Build error messages should be clear.** When a recipe JSON is missing a required field, the build error should name the file and the field. Don't fail with a stack trace.
- **No TypeScript, no React, no Vite, no esbuild.** This is intentional. The project is static HTML rendered from JSON via Python templates; complexity should be in the recipe content, not the toolchain.
- If anything in HANDOFF_01 conflicts with `SPEC.md` v0.1, the SPEC wins. Surface the conflict; do not silently resolve.
